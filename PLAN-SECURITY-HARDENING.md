## Revision 2: keeping the vendor key out of the app (key custody)

Added 2026-10-29 after owner feedback: "I had to pass the raw key into SpeechKit, which is ripe for targeting." Reviewed and corrected in Revision 3 on 2026-10-29. Server custody is the distribution requirement for an app-owned vendor key; the transport and lifecycle fixes below are prerequisites, not work to defer until Phase K is finished.

### The problem and trust boundaries

A long-lived vendor key supplied to the app is available to that app's process. `.apiKey` is not itself the vulnerability; distributing your shared billing credential is.

- Compiled literals, bundled configuration and build artifacts can expose a key through static inspection. Obfuscation only raises extraction cost. Source control, CI artifacts and logs are independent exposure paths.
- Fetching the same permanent key from a backend, encrypting it with an app-held decryption key, or storing it in Keychain does not change who ultimately receives it. Keychain protects storage and app isolation on an uncompromised device; it does not protect a key after authorized retrieval into a compromised process.
- A debugger, injected code or Frida can intercept resolved strings, request construction, headers, WebSocket frames or TLS calls where the attacker can instrument the process. Stock release-app protections constrain this; not every iPhone permits arbitrary debugger attachment. Jailbroken devices and attacker-controlled desktop environments remain in the threat model.
- A TLS-intercepting proxy can read credentials and audio if its root is trusted by the device/app and pinning does not reject it. Installing a certificate alone is not sufficient on every platform. Passive network observers cannot read HTTPS/WSS headers or query strings. Pinning does not defeat instrumentation before encryption.
- A stolen key gives the holder the permissions, project/model access and spending authority actually granted to that key. It does not necessarily authorize every model or account action. Vendor restrictions, expiry and revocation can limit it; a broadly permitted reusable key can still cause substantial loss.
- Short-lived vendor tokens, relay tickets, upload capability URLs and session-resumption handles are also secrets. Expiry limits a window, not necessarily session duration, use count, model access or spend. A stolen bearer credential can be replayed from another device unless the accepting server enforces proof of possession.

Opaque Swift APIs, redaction, Keychain and reset reduce accidental exposure. They cannot make an app-owned vendor key inaccessible to hostile code executing in that app. Apple on-device transcription needs no vendor credential; SpeechKit's current Apple implementation requires iOS/macOS/visionOS 26 and is not available on watchOS, despite the package's lower deployment targets.

Existing `.token(SpeechTokenProvider)` and endpoint overrides are useful building blocks, not a complete secure broker/relay API. A closure can return a permanent key. Auth placement is provider-specific, Gemini has auxiliary routes, and several native token modes do not match current request builders. Do not tell apps that merely changing `.apiKey` to `.token` fixes custody.

### Decision rule

| App / capability | Credential approach |
| --- | --- |
| User-owned key, including BYOK tools and the demo | Direct use from Keychain is an explicit user policy. Explain vendor permissions, billing, rotation and privacy. An internal app carrying the company's shared key is still an app-owned-key case. |
| App-owned key; a documented native client token supports the exact endpoint/model, and its enforceable restrictions meet the app's abuse budget | Pattern A, token broker. The server mints the vendor token; audio goes directly to the vendor. ElevenLabs supports both batch and realtime tokens. OpenAI and Gemini support realtime tokens; Mistral documents model-scoped realtime tokens with the version qualification below. |
| No documented suitable native token, or hard per-user duration/spend/configuration controls are required but the vendor token cannot enforce them | Pattern B, relay. The vendor key remains server-side and every billable operation passes through server enforcement. This includes most file routes, but not all. |
| Apple local transcription meets the feature/platform requirements | No vendor key, broker or relay. |

**Pattern A, token broker**

The app authenticates to the backend. The backend authorizes the account and requested capability, checks replay-resistant app/device proof where supported, reserves issuance/usage budget, and mints a token using a server-held key. Return only the client token and nonsecret expiry/scope metadata with `Cache-Control: no-store`. Resolve just before connecting; do not prefetch single-use tokens into a shared pool.

The broker records issuance against the user, but the vendor may see only a bearer token for the app's project. This does not make it cryptographically bound to that user/device at the vendor. A stolen token may support multiple sessions. A single-use token may still authorize a long or expensive request, and an attacker can race the legitimate client to consume it. Broker-side issuance quotas alone cannot enforce actual audio duration, concurrency or spend after direct connection. Use a relay when vendor controls cannot supply the required bounds.

**Pattern B, relay**

The app exchanges its normal login credential for a short-lived, relay-audience transcription ticket restricted to the user, provider, capability and allowed operation. Do not send a general account session or refresh token through provider-shaped request builders. The new K2 mode authenticates HTTPS requests and WSS upgrades with `Authorization: Bearer <relay-ticket>`, independent of upstream auth.

The relay verifies the ticket and any bound request proof, authorizes the operation, reserves quota atomically, and selects an upstream from server configuration. It strips client credentials from headers, query items, subprotocols and protocol frames, then supplies only the appropriate vendor credential. Meta requires rewriting the first JSON handshake; WebSocket byte pass-through alone cannot do this. Filter subsequent configuration messages as well as the initial request.

A stolen bearer relay ticket can consume the victim's remaining quota and, if badly scoped, read their job results. Short expiry, revocation, object ownership and request proof reduce this risk. Do not claim theft is harmless or necessarily attributable to the legitimate user.

### Controls required before broker/relay deployment

| Risk | Required control and limit |
| --- | --- |
| App Attest bypass, unsupported platforms and replay | Check `isSupported` and availability on each supported target; define an explicit server-enforced fallback for unsupported devices, simulator and desktop distribution. Do not silently grant full access when attestation fails or a client reports it unavailable. Validate Apple's chain, app identity, environment, challenge and assertion counter server-side. Bind fresh assertions to canonical request data and account/ticket identity. Frida can bypass local checks or invoke legitimate signing paths on a compromised instance; it does not thereby forge Apple's signatures or extract the Secure Enclave key. Attest is an abuse signal and request-origin proof, not user authentication, ongoing runtime-integrity proof or a guarantee against device farms. See [A1]–[A2]. |
| Token theft and replay | Short TTL and narrow audience/scope; separate login, broker and relay credentials. Atomically consume one-use tickets/challenges and enforce counters. Bind relay tickets to an attested key or another proof-of-possession key and require a fresh signed request/upgrade proof. Binding only at issuance does not prevent later bearer-token replay. Native vendor tokens are not App-Attest-bound unless the vendor actually verifies such proof. Protect resumption handles and upload tickets too. |
| Cost and resource exhaustion | Enforce per-user, per-device and aggregate issuance, concurrency, byte, decoded-audio-duration and wall-clock limits. Reserve quota atomically before minting/opening upstream; reconcile usage conservatively on unknown outcomes. Cover idle sockets, oversized/chunked uploads, channel count, expensive models/options, repeated retries and account/device farming. Backpressure, bounded buffers, deadlines and upstream cancellation are required. Vendor budgets may be alerts or delayed controls rather than hard caps. Use isolated vendor projects, least-privilege keys, alerts, rotation and a server kill switch; stopping minting may not stop already-issued tokens/sessions. |
| Open proxy, SSRF and credential forwarding | Fixed provider/route/model allowlists, no caller-selected upstream host, absolute URL, arbitrary method, path traversal or generic CONNECT. Validate DNS/IP destinations and redirects, including returned upload-session URLs, against provider-specific approved egress; enforce the approved address at connection time to prevent DNS rebinding and block private/link-local/metadata targets. Do not rely only on suffix matching. Disable arbitrary source URLs, callbacks and remote tools unless separately authorized and validated. Bind every upload/job identifier to its user. Strip unapproved query/header/frame fields and never return vendor keys in errors or upstream URLs. |
| Audio/transcript privacy | A TLS-terminating relay sees plaintext audio and transcripts. Disclose that extra processor and its region/retention policy. Default to no body/transcript/query-token logging, no edge cache, bounded memory buffering and protected temporary storage with cleanup. Audit APM, traces, crash/error reporting, access logs and backups. Keep operational usage metadata minimal. Define deletion/expiry for relay jobs and vendor uploads, including failed/cancelled requests; SDK reset does not delete server copies. A relay is not end-to-end encryption between device and vendor. |

Gemini's `fileEndpoint` configures Interactions, not the binary upload. `GeminiFileTranscriptionClient.swift:493` derives interaction polling by removing a terminal `/interactions`. `GeminiFilesClient.swift:201` derives file polling by removing `/upload/` and the terminal `files` segment. The relay must consume Google's `X-Goog-Upload-URL` internally and return its own HTTPS upload-session URL. Current upload/finalize at `GeminiFilesClient.swift:154` sends no Authorization header: that returned URL is itself a bearer capability. In K2, attach the relay ticket/proof only to the validated relay destination and bind the opaque upload ticket to the operation, size and user. Do not attach app auth to Google's capability URL. Map returned file names/URIs and interaction IDs through a per-user registry; reject foreign or caller-invented resources. Never fetch an arbitrary URI embedded in an Interactions body.

Test inline, forced Files API and threshold-selected `.automatic`, pending-file polling, background-interaction polling, malicious returned URLs, expired capabilities, cancellation and mixed configuration. A complete configuration does not by itself prove auxiliary responses stay on the relay.

### Severity decisions and qualifications

- SK-01 stays High because a recoverable credential-shaped value warrants rotation even without proof it is live. Its presence is confirmed; compromise is not. Both commits are reachable only through local `refs/t3/checkpoints/` refs among the refs inspected. Neither is a HEAD ancestor. The owner has already been told about this `.env` finding; this plan does not present it as a new discovery.
- SK-02 stays High because an ordinary redirect can disclose a reusable key to another origin. A proxy/edge must return that redirect; there is no demonstrated attacker-controlled redirect on a vendor. The loopback HTTP probe proves Darwin file-request behavior, not every WSS/HTTPS implementation on all platforms. WebSocket redirect leakage remains a test requirement under this finding.
- SK-10 rises from Low to Medium. False success on credential deletion is a direct failure of the demo's security control, not just optional cleanup. The failed-operation condition was established in code, not through device Keychain fault injection.
- SK-17 falls from Medium to Low for this repository. Supply-chain hardening is worthwhile, but provider secrets are absent from CI, repository defaults are unknown, and elevated token privileges were not established.
- SK-18 falls from Medium to Low for this key-safety review. The missing declaration can block app distribution but does not disclose credentials. Recheck the applicable Apple reason before release.
- All other original severities are retained. SK-04 and SK-08 stay Medium because account/configuration changes or a varying broker are required. SK-12 stays Low because raw getters are not an isolation boundary against hostile native code.
- SK-14 remains Low for the SDK compatibility defect, but is a release prerequisite for advertising the native-token custody path. Revision 3 replaces the earlier snapshot uncertainty with the dated matrix: Google explicitly accepts the Token header on the constrained method; ElevenLabs batch tokens use a query parameter; Mistral realtime tokens use a subprotocol. OpenAI client secrets support transcription sessions but are reusable and do not lock client-overridable configuration. Mistral model-version acceptance and xAI STT-token support remain explicit contract gaps, not inferred support.
- SK-15's session defaults and SK-22's missing cover are confirmed source facts. Their proposed disclosure consequences remain Plausible. Neither should be reported as a demonstrated key leak.

### New gaps and duplicate boundaries

SK-11 differs from an arbitrary endpoint override or redirect: the SDK chooses a second destination automatically. `GeminiFileTranscriptionClient` independently defaults its `GeminiFilesClient` to Google's endpoint. `.automatic` switches by file size. A proxy-only credential reaches Google in upload initiation even if Google rejects it; audio proceeds there only if initiation succeeds. This is a configuration footgun, not an undocumented promise that one override covers both endpoints: `README.md:150` already explains `filesEndpoint`. The same problem exists in reverse when only `filesEndpoint` is overridden. A proxy configuration should validate the complete route before fetching a credential or uploading bytes.

SK-25 concerns the demo's avoidable Keychain-to-memory loading, separately from the SDK's public credential ownership in SK-12. The demo loads unused providers and retains them for the view lifetime. It can improve without changing SDK API. Changing the Keychain class alone leaves these copies readable by the running app.

Post-stop realtime keys and closure captures are not new findings: C4 already covered them, now SK-12. WebSocket URL credentials are already SK-06 and SK-05. `@Sendable` does not make a callback secret-free or short-lived; it may retain an actor, backend session, or even a static vendor key. Releasing all SDK references can release its captures, but cannot release host-owned copies.

## Key-handling design principles

- [ ] Keep app-owned vendor keys server-side. Choose a relay or a native token with documented capability/audience, expiry and reuse semantics that meet the abuse budget. Token configuration defaults are not necessarily locked permissions. Fetching a permanent vendor key from a backend does not make it short-lived.
- [ ] Use headers for credentials whenever the protocol supports them. Never put a long-lived key in a generated URL. Document required short-lived query-token exceptions, including ElevenLabs realtime and batch, and protect URLs as secrets. Gemini Live tokens support a Token header on the constrained method; Mistral realtime tokens use a subprotocol. Redact all of these credential locations. Meta's first-frame authorization is a separate protocol exception over a verified approved WSS connection.
- [ ] Validate all destinations before fetching/attaching credentials. Require TLS, reject URL userinfo, and treat every proxy host as an explicit secret recipient. Validate returned upload URLs and all auxiliary endpoints too.
- [ ] Reject cross-origin redirects and TLS downgrades by default. Authorization headers, custom key headers, capability URLs, and audio bodies all need replay controls.
- [ ] Default to no persistent SDK cache, cookies, or ambient authentication sharing. Custom transport options cannot silently disable destination checks.
- [ ] Give credential/configuration/request holders safe descriptions, debug descriptions, and mirrors. Do not log secrets, request URLs, raw server error strings, or audio/transcripts by default.
- [ ] Public errors carry safe categories/status, not arbitrary server or callback payloads. Sanitizing only `localizedDescription` while retaining a raw underlying error is insufficient.
- [ ] Resolve one identity per operation, bind it to an immutable complete-route snapshot, and invalidate pending work on reset/reconfiguration. Recheck generations after every suspension. Renew only under K4's explicit no-side-effect/idempotency rules; never blindly replay audio or share a single-use token across concurrent starts.
- [ ] Broker issuance and relay operations require server-side account authorization, replay controls and atomic budgets. App Attest complements those controls; it does not bind vendor bearer tokens or prove ongoing runtime integrity. Relay privacy and SSRF controls are deployment requirements.
- [ ] Keep credentials and callback captures only as long as needed. Define stop, reset, discard, and host-owned copy lifetimes. Do not call deferred key lookup an ephemeral credential without a real expiry contract.
- [ ] Test with synthetic sentinels and controlled servers. Include redirect, cancellation, reconfiguration, errors, reflection, and provider-specific auth-placement tests before adding a provider.

## Explicitly out of scope / accepted risks

- **Guaranteed zeroization is not achievable with the current Swift String/Foundation model.** Copy-on-write buffers, interpolated headers, encoded JSON, task captures, URLRequest copies, allocator behavior, OS paging and diagnostics can retain bytes. Clearing a property reduces reachability; it does not prove memory erasure. Do not advertise zeroization or treat secure-buffer wrappers as solving all copies.
- **A client holding a long-lived credential is inherently exposed to its user and compromised in-process code.** Keychain protects storage, and opaque APIs reduce accidental sharing. Neither makes app-bundled vendor credentials safe. User-supplied keys can remain an explicit application policy with scope/rotation guidance.
- **No confirmed credential data race was found.** Public services/facade are MainActor-isolated, sockets are actors, and `SpeechTokenProvider.fetch` is `@Sendable`. SK-04 is actor reentrancy across awaits, not a missing Sendable annotation. Fish's unchecked-Sendable socket wrapper contains immutable Foundation session/task references. Audio-manager concurrency merits a separate audio correctness review; it does not establish a key leak.
- **Closure captures are retained but ordinary reflection does not expose them.** The supplied probe confirms this distinction. Token-provider equality compares IDs and does not fetch or log credentials. Credential/configuration types do not synthesize Hashable or Codable exposure. Failed assertion formatting belongs to SK-03, not an independent hashing or remote timing vulnerability.
- **Test helpers are not a demonstrated real-key leak.** Request-recording URLProtocol helpers use locks and synthetic credentials, e.g. `Tests/SpeechKitTests/GeminiProviderTests.swift:922` and `FishAudioProviderTests.swift:704`. Keep them synthetic; request/header assertions would be unsafe if real credentials were introduced. No environment/Keychain-backed integration keys were found in the reviewed tests.
- **The extension bag is not a vault.** `SpeechServiceExtensionStorage.swift:43` allows name/type-based readback but stores no built-in provider credentials. Native extensions share app trust. A separate plugin sandbox is outside this SDK plan.
- **TLS does not hide content from the selected provider or a trusted TLS-terminating proxy.** Passive network observers do not see HTTPS/WSS query contents. System certificate validation remains appropriate; mandatory vendor certificate pinning is not proposed for a multi-provider/proxy SDK. K11 permits optional pinning to the app's own relay/broker with host-owned rotation and backup-pin policy. It does not promise protection against a hooked client process.
- **No automatic SDK plaintext key persistence was found.** The demo uses Keychain, not UserDefaults, for keys. SDK upload bodies are built in memory and caller-owned recordings remain caller-owned. Foundation caching remains SK-15; OS internals were not forensically inspected. Temporary demo WAVs are normally excluded from backups, while Documents smoke artifacts are not.
- **Public file errors do not generally retain entire NSError userInfo.** `SpeechService+FileTranscription.wrap` at line 853 discards ordinary file error metadata and uses a constant timeout message. Unsafe reason/description text still survives. Realtime raw errors have a broader exposure path.
- **Server implementation and vendor retention remain separate verification boundaries, not omitted design responsibilities.** K5/K10 require broker minting, relay authorization, budgets, replay/SSRF controls and audio/transcript retention/deletion policy before deployment. This review does not audit a deployed relay, vendor retention behavior, demo dependencies or telemetry configuration. Clearing client data does not delete server copies. No automatic token-to-key downgrade was found. No authenticated speech-to-text requests, paid canaries or real-key validation were performed here.
- **No legacy Apple speech-permission defect is established.** The implementation uses SpeechAnalyzer/SpeechTranscriber, not the legacy SFSpeechRecognizer authorization path. Device permissions/privacy disclosures remain an app release responsibility.
- **App screenshots and user exports cannot be universally prevented.** An app-switcher cover limits incidental snapshots; it is not a general screenshot blocker or protection for copies the user intentionally exports.
